# 物流研究助手 · 编排层消融评测

这个目录回答一个问题：**六环节里到底哪一环在起作用，各值多少。**

不是「跑几个问题看看答案对不对」——那种做法只能给出个别案例，没法支撑任何结论。
这里要的是可复现的数字：同一份证据、同一套题，只改编排策略，看指标怎么动。

## 一、为什么要「录制 + 回放」

真实链路是三路工具 + 五个模型节点串起来的。如果每换一组策略就重新取证一遍，
差异里就混进了「这次 web 恰好搜到了什么」「这次 SQL 多查了 8 秒」这类噪声，
而且每轮要重跑 40 题 × 4 个服务，几个小时起步。

所以拆成两段：

```
record  真实调用三路工具，把每次 (路, 问题) → 证据 落盘
   ↓
replay  六组策略共用同一份证据池，只换 plan / compress / review 三个节点
```

这样证据完全相同，差异只能来自编排本身——控制变量，而不是碰运气。

一个副作用是成本：取证只花一次钱。40 题录制约 = 400 次工具调用，
回放阶段只剩压缩与报告生成。

## 二、题库：40 题，五层

题库在 `qa_set.jsonl`。每一题都带「可自动核对的事实清单」和「人工确认过的参考答案」，
出处记在 `source` 字段里（大部分直接来自履约知识助手 164 题标注集与仓配自助问数 56 题 NL2SQL 标注集，
数仓题的期望值是我拿 gold SQL 实跑出来的结果）。

| 分层 | 题数 | 考什么 | 判分依据 |
|---|---|---|---|
| 单源·知识库 | 12 | 仓储装备手册里的参数、故障码、操作边界 | 事实清单（参数值 / 报警码 / 关键结论） |
| 单源·数仓 | 12 | NL2SQL 经仓配自助问数返回后的数值是否正确 | 事实清单（数值，2% 容差） |
| 多子任务复合 | 8 | 一个问题里三件事，规划能不能拆开、逐项覆盖 | 事实清单（每个分句一条） |
| 需联网 | 4 | 语料里没有、只能靠外部检索的问题 | LLM 判分（不设事实清单） |
| 不可答 | 4 | 数据与语料里确实没有的信息 | 是否明确承认查不到 |

**为什么没有「跨源双答」的题**：履约知识助手语料是仓储装备手册与作业规范，
仓配自助问数是同一家公司的仓配履约数仓——虽然同属物流域，但两路回答的是**完全不同形态的事实**：
一路是"这台设备额定载荷多少"，一路是"这个大区出了多少货值"。
硬造一道「两个源都能答」的题，只会得到一道两路都答不上的题，指标毫无意义。

所以这里换了个更接近真实价值的问法：**能不能在只有一路有货时不跑偏**。
第三层考的是「一个问句里的多个分句分散在不同切片」，
第五层考的是「查不到时会不会编」——后者比前者更能暴露问题，
因为自主 agent 最常见的翻车不是答错，是答得很像样但没根据。

## 三、六组消融

| 组 | 规划 | 压缩 | 审查 | 这一组回答的问题 |
|---|---|---|---|---|
| G1 单智能体一把梭 | 单任务 | 不筛选 | 关 | 基线：一个 agent 直接调三个工具 |
| G2 +多子任务规划 | 录制规划 | 不筛选 | 关 | 规划单独值多少 |
| G3 +跨源去重 | 录制规划 | 去重 | 关 | 去重单独值多少（配额仍关） |
| G4 +按路配额 | 录制规划 | 去重 + 配额 | 关 | 配额与轮转值多少 |
| G5 +审查回环 | 录制规划 | 去重 + 配额 | 开 | 审查值多少（= 线上配置） |
| G6 完整但关去重 | 录制规划 | 配额，不去重 | 开 | 留一法：其它都在，只抽掉去重 |

G2–G5 是累加式阶梯，每一级只加一层；G6 是反向对照。
只做累加式消融容易得出「每一层都有用」的漂亮结论，
留一法能看出某一层在其它层都在时是否还必要。

G1 的规划是确定性的（不调模型，直接一个 todo 三路全上），
G2–G6 用的是**录制时同一份规划**，所以各组之间的差别不在「这次拆得好不好」，
而在拆完之后怎么处理证据。

## 四、指标口径

能算的都用规则算，只有「表达是否忠实」交给模型：

| 指标 | 算法 | 为什么这么定 |
|---|---|---|
| 关键事实命中 | 事实清单逐条匹配：文本型比对归一化子串，数值型允许 2% 误差并支持万/亿换算 | 规则可复现、零成本；模型判「2,636,218.99」和「约 263.6 万」是否相同并不可靠 |
| 引用有效率 | `1 - 越界编号数 / 引用总数` | 越界引用是硬伤：读者以为有出处，其实没有 |
| 段落引用覆盖 | 正文中含 `[n]` 的实质段落占比 | 标题、表格、参考来源节不计入，否则所有组一起虚高 |
| 路由命中 | 期望路由是否取到 >0 条证据 | 调用成功但返回空，对回答没有帮助 |
| 忠实性 / 覆盖度 / 诚实性 | LLM 判分 0~2 分，三项分开 | 合成一个总分会让「答得全但都在编」和「答得少但都有据」同分 |
| 回放缺失 | 回放时池子里没有的调用数 | 必须显式暴露：有缺失说明这组问出了录制时没问过的问题，实验设计有问题 |

判分模型：`LLM_JUDGE_MODEL_NAME`，默认 **`qwen-plus`**。

> ⚠️ **这一条改过。** 早期为了省钱，判分模型直接复用了 `LLM_EVAL_MODEL_NAME`（默认 `qwen-flash`），
> 而那一轮的被测主链也是 `qwen-flash` —— 等于让模型给自己写的报告打分。
> 两个问题叠在一起：同族模型的**自我偏好偏差**，加上最便宜的档位做 0~2 分 rubric 判定的**噪声**。
>
> 现在拆成独立配置，且 `meta.json` 会记录 `judge_same_as_main`；两者相同时控制台直接告警。
> **`eval/results/full/` 那一轮是旧配置跑的（`judge_same_as_main: true`）**，
> 所以它的读法是「同一判分器下的相对比较」——组间高低比绝对值可信，绝对水平未经独立验证。
>
> 还没做：用 plus 重跑一轮、抽 10 题人工复核报 judge-human 一致率。这是本套评测最大的短板。

## 五、结果（40 题，qwen-flash，回放同一证据池）

| 组别 | 关键事实命中 | 段落引用覆盖 | 覆盖度 | 平均 token | 平均工具调用 |
|---|---|---|---|---|---|
| **G1 单智能体一把梭** | **90.1%** | 66.7% | 2.00 | 4676 | 3.00 |
| **G2 +多子任务规划** | **91.7%** | 74.6% | 1.98 | 4007 | 2.48 |
| G3 +跨源去重 | 89.1% | 83.3% | 2.00 | 2706 | 2.48 |
| G4 +按路配额 | 84.9% | **85.8%** | 1.98 | **2547** | 2.48 |
| G5 +审查回环（完整） | 88.0% | 75.0% | 2.00 | 4843 | 5.40 |
| G6 完整但关掉去重 | 91.7% | 77.9% | 2.00 | 5627 | 5.33 |

**逐级贡献**（每一级相对上一级）：

| 这一级加了什么 | 事实命中 | 相对上一级 | 平均 token | 相对上一级 |
|---|---|---|---|---|
| 多子任务规划 | 91.7% | +1.6 个点 | 4007 | -14% |
| 跨源去重 | 89.1% | **-2.6 个点** | 2706 | **-32%** |
| 按路配额 | 84.9% | **-4.2 个点** | 2547 | -6% |
| 审查回环（完整） | 88.0% | +3.1 个点 | 4843 | +90% |
| （留一法）关掉去重 | 91.7% | **+3.6 个点** | 5627 | +16% |

### 这一轮结论和上一轮不一样，如实记录

换到仓储物流语料后，**完整链路（G5）在关键事实命中上不再是最高的**（88.0%，
低于 G2/G6 的 91.7%，也低于 G1 基线的 90.1%）。原因不是编排变差了，而是这批题**更容
易答**：单源·知识库层 12 题的期望值都在同一份手册里，三路全上的 G1 天然就能撞对。

真正稳定成立的结论有四条：

1. **多子任务规划是唯一在事实命中上为正的一级**（+1.6 个点），同时 token 还降了 14%。
   一问三答的复合层能做到 87.5% 事实命中，说明拆分确实有效。
2. **去重和配额是用准确率换 token**：两级合计把平均 token 从 4007 压到 2547（-36%），
   但事实命中累计掉 6.8 个点（91.7% → 84.9%）。代价换来的收益是**段落引用覆盖从 74.6%
   涨到 85.8%**——报告不再被某一路的长文本挤满，每个实质段落都有出处。
   值不值取决于场景：看「有没有引到」选 G4，看「有没有答全」选 G2。
3. **审查回环把去重丢掉的分救回来一半**（84.9% → 88.0%，+3.1 个点），
   代价是 token 涨 90%、工具调用翻倍（2.48 → 5.40）。它是唯一会让单次问答成本翻倍
   的环节，适合合规、医疗这类「宁可多查一轮」的场景。
4. **留一法这次推翻了「去重必要」的旧结论**：其它层都在时关掉去重，事实命中反而
   **涨 3.6 个点**（88.0% → 91.7%）。因为配额已经先吃掉了一部分重复，
   再去重只会把本就稀缺的证据裁掉。上一轮在 IT 设备语料上这个差值是 -1.6，
   本轮是 +3.6——**同一套代码，换一批题结论就翻面**，这条本身就是样本量局限的证据。

### 引用有效率这次有了区分度

| G1 | G2 | G3 | G4 | G5 | G6 |
|---|---|---|---|---|---|
| 100.0% | 100.0% | **97.4%** | **96.3%** | 100.0% | 100.0% |

上一轮六组都是 100%，没有区分度。这一轮 G3/G4 掉到 97.4% / 96.3%，
说明**压缩环节会裁掉报告实际引用到的证据**——去重与配额按相似度裁剪时，
把编号也一并重排了，报告层偶尔会引用到已经不存在的编号。
这是本轮新暴露的一个缺陷，也是压缩策略下一步要修的地方。

### 分层看，瓶颈在哪

| 分层 | 题数 | 事实命中 | 说明 |
|---|---|---|---|
| 单源·知识库 | 12 | 93.1% | 手册类语料上基本到位 |
| 单源·数仓 | 12 | 83.3% | **上限由仓配自助问数的 NL2SQL 决定，不是编排** |
| 多子任务复合 | 8 | 87.5% | 一问三答，说明拆分确实有效 |
| 需联网 | 4 | — | 不设事实清单，只判忠实性（诚实性 1.00/2，本轮偏低） |
| 不可答 | 4 | — | **4/4 明确承认查不到**，没有编造 |

数仓层仍是瓶颈，且掉分主要来自下游而不是编排：部分题目仓配自助问数生成的 SQL 命中了
相邻字段（如把"运费"查成"货值"），编排层救不回来——
物流研究助手能做的是把 SQL 原文一起放进引用（`ref` 字段就是实际执行的 SQL），让错误可追溯。

需联网层的诚实性只有 1.00/2，明显低于其它层。这 4 题问的是宏观统计与政策口径，
外部检索拿到的多是二手转述，报告照抄就容易被判「缺乏权威来源」。
这一层的分数更反映外部信息源质量，不宜当作编排能力的指标。

不可答层 4 题全部明确说「查不到」而不是编一个数，这是这套系统里最值得写进简历的一条：
自主 agent 最常见的翻车不是答错，是答得很像样但没根据。

### 实测成本

| 阶段 | 耗时 | 消耗 |
|---|---|---|
| 录制 40 题 | 约 28 分钟 | 303 次取证调用、编排 23.5 万 token |
| 回放 6 组 × 40 题 | 约 15 分钟 | 每组 2.5k~5.6k token/题，另加 240 次判分调用 |

按百炼单价折算，整轮（录制 + 六组回放 + 判分）在**十元以内**。
贵的是时间不是钱：录制阶段每一题都要打一次仓配自助问数的 NL2SQL 链路（单次 8~15 秒）。

## 六、怎么跑

```bash
# 1. 录制（真实调用，约半小时，需要履约知识助手 :8001 / 仓配自助问数 :8010 在线）
python -m eval.run_eval record

# 2. 回放六组 + 判分（约半小时）
python -m eval.run_eval replay

# 3. 用已有产物重新出表
python -m eval.run_eval report

# 冒烟：前 8 题，只跑两组
python -m eval.run_eval record --limit 8
python -m eval.run_eval replay --limit 8 --variants G1,G5
```

常用参数：`--ids k01,s01`（只跑指定题）、`--variants G1,G5`、
`--no-judge`（跳过模型判分，零模型成本）、`--force`（重录已有证据池）。

产物在 `eval/results/<run-id>/`：每组一个逐题 JSON、`summary.csv`、`report.md`。

## 七、已知局限

1. **样本量**：40 题分五层，每层只有 4~12 题。层内差异几个百分点的，
   不要当成结论——这也是为什么主表看总体，分层表只用来定位问题出在哪类题上。
2. **回放的固有偏差**：审查回环依赖「补检索」，而录制只有 2 轮。
   回放时如果审查在最后一轮还要补，会被截断并记一条 note，
   所以 G5/G6 的审查贡献是被**低估**的。
3. **单一语料**：履约知识助手是 36 份仓储物流装备手册与作业规范（145 个切片），
   仓配自助问数是同一家公司的仓配履约数仓。结论能说明「编排在这类语料上的表现」，
   不能外推到开放域研究。同一套代码在 IT 设备语料上跑出的结论与本轮**方向相反**
   （见上文第 4 条），这本身就说明单批 40 题的结论不宜过度推广。
4. **判分主观性**：LLM 判分有随机性，同一份报告两次可能差一档。
   所以事实命中率是主指标，判分只作辅助；两者冲突时以规则指标为准。
   诚实性一项只在「不可答」层有解释力，其它层的分数受判分模型对
   「表格数据算不算有据」的判断影响，不必过度解读。
5. **一个本轮新暴露的缺陷**：去重与配额（G3/G4）会让引用有效率从 100% 掉到
   96.3%~97.4%——压缩重排证据编号后，报告层偶尔引用到已不存在的编号。
   这是压缩策略的真实缺陷，尚未修复，如实记录。
6. **数仓层的天花板在下游**：12 题里的事实命中 83.3%，失分点集中在仓配自助问数的
   NL2SQL 选错字段/口径，编排层无法补救。评估编排能力时应把这一层单独看。

## 八、自检

```bash
python -m unittest tests.test_eval -v
```

27 项断言钉住口径：数值容差、去重开关是否真的生效、
引用统计是否把标题算进分母、回放缺失是否被判为不可重试等。
评测代码错了会让整张表变成一堆看着合理但结论全错的天文数字，
所以这部分和主链路一样要有测试。
